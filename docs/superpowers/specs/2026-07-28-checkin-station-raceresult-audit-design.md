# Check-in Station, RaceResult Sync, and Audit Design

Date: 28 July 2026

Status: Approved design, pending written-spec review

## Objective

Extend HYFIT check-in so administrators can create named check-in counters and
assign volunteers to them. Every completed check-in must retain complete,
immutable local audit evidence while sending only the required operational
fields to RaceResult 14.

## Scope

This change includes:

- centrally managed check-in counters per event;
- one active counter assignment per check-in volunteer per event;
- server-side resolution of the volunteer's assigned counter;
- immutable volunteer, counter, participant, device, and asset audit snapshots;
- durable RaceResult POST operations for exactly three fields;
- visible local and RaceResult synchronization states;
- assignment history and safe volunteer reassignment;
- migrations, API validation, UI changes, and automated tests.

It does not add automatic high availability, change the participant import
format, or make RaceResult the store for HYFIT audit metadata.

## Core decisions

### RaceResult fields

Completing check-in creates exactly three RaceResult field updates:

| Field name | Value |
|---|---|
| `checkinstatus` | `1` |
| `wristbandid` | Scanned wristband ID |
| `Transponder1` | Scanned Transponder1 ID |

Field names are case-sensitive. In particular, the default must be
`Transponder1`, not `transponder1`.

The existing event update mapping may override these names only when an
administrator explicitly publishes a different RaceResult mapping. The default
Admin mapping and seed data must use the exact names above.

Each update is sent as an HTTP POST to the event's complete RaceResult update
endpoint with these query parameters:

```text
bib=<participant BIB>
fieldname=<field name>
value=<new value>
nohistory=0
```

No volunteer, counter, device, or internal audit data is posted to RaceResult.

### Local-first transaction

The local database remains available when RaceResult or the internet is
unavailable. One PostgreSQL transaction must:

1. lock and validate the participant;
2. resolve and validate the authenticated volunteer's active counter;
3. release superseded active asset assignments when an authorized replacement
   workflow applies;
4. create the wristband and Transponder1 assignments;
5. create the immutable check-in record and its audit snapshots;
6. create the three idempotent outbox operations;
7. set the participant to `pending_sync`;
8. append a structured audit event.

If any local step fails, none of the steps commit. RaceResult calls occur only
after commit through the worker. A RaceResult outage therefore cannot discard a
locally accepted check-in.

## Data model

### `checkin_stations`

Add an event-scoped station table:

- `id`: UUID primary key;
- `event_id`: required event reference;
- `code`: short operator-facing code such as `C01`;
- `name`: display name such as `Main Gate`;
- `enabled`: whether new assignments may use the station;
- `created_by`: administrator reference;
- `created_at` and `updated_at`: server timestamps.

Station code is unique per event, case-insensitively. A station with historical
records is disabled rather than deleted.

### `checkin_station_assignments`

Add a history-preserving assignment table:

- `id`: UUID primary key;
- `event_id`: required event reference;
- `station_id`: required check-in station reference;
- `volunteer_id`: required user reference;
- `assigned_by`: administrator reference;
- `assigned_at`: authoritative server timestamp;
- `released_at`: nullable server timestamp;
- `release_reason`: nullable administrator-entered reason.

A partial unique index permits only one active station assignment for a
volunteer in an event. Multiple volunteers may be assigned to the same station.

Reassigning a volunteer closes the current assignment and creates a new one in a
single transaction. It never rewrites earlier check-ins.

### `checkins`

Extend each check-in with evidence that remains meaningful even if users,
participants, sessions, or stations are later renamed:

- `station_id` and `station_assignment_id`;
- `session_id`;
- `transaction_id`, globally unique and generated by the server;
- `participant_bib_snapshot`;
- `participant_name_snapshot`;
- `volunteer_staff_id_snapshot`;
- `volunteer_name_snapshot`;
- `station_code_snapshot`;
- `station_name_snapshot`;
- `wristband_code_snapshot`;
- `transponder1_code_snapshot`;
- `device_label_snapshot`;
- `source_ip_snapshot`;
- `client_observed_at`, optional diagnostic browser timestamp;
- existing `verified_at` as the authoritative completion time;
- event timezone snapshot;
- synchronization state.

Server time is authoritative for ordering and audit decisions. The optional
browser timestamp is diagnostic only and must never replace `verified_at`.

Existing installations receive a forward-only migration. Historical rows may
retain null snapshot values where the original evidence cannot be reconstructed
reliably; the migration must not invent it.

### Session identity

Authentication must expose the current session ID internally so the check-in
handler can link the transaction to the exact login session. The API must obtain
the session, device label, and source IP from authenticated server state. It
must not accept them as authoritative request-body fields.

## Admin workflow

The event Admin dashboard gains a **Check-in counters** area:

1. Create a counter with a unique code and descriptive name.
2. Enable or disable a counter.
3. Assign an enabled check-in volunteer to a counter.
4. Reassign a volunteer with a required reason.
5. See the current volunteers at each counter.
6. See assignment history with assigning administrator and timestamps.

Only `super_admin` and `event_admin` roles may create counters or change
assignments. Only enabled users with the `checkin` role and the same event may
be assigned.

The Admin team list displays each check-in volunteer's current counter. A
counter cannot be hard-deleted after it has assignments or check-ins.

## Volunteer workflow

After authentication, the check-in page fetches the volunteer's current
assignment and displays:

- station code and name;
- volunteer name and staff ID;
- local-server connectivity state.

A volunteer without an active enabled station assignment may look at the page
but cannot complete a check-in. The page clearly says that Admin must assign a
counter.

The check-in request contains only participant and scanned asset inputs plus an
optional client-observed timestamp. It does not submit a trusted desk name or
station ID. The server derives the counter from the authenticated volunteer.

On completion, the response returns:

- transaction ID;
- BIB;
- local acceptance timestamp;
- station code and name;
- synchronization summary for the three RaceResult operations.

The confirmation message distinguishes:

- **Saved locally — RaceResult sync pending**
- **RaceResult confirmed**
- **RaceResult requires attention**

The initial response normally reports pending because the durable worker sends
updates after the local transaction commits. A status endpoint allows the page
to observe confirmation without resubmitting the check-in.

## Outbox and synchronization

Operation keys use the immutable check-in transaction identity and canonical
purpose, rather than a mutable display field:

```text
checkin:<transaction-id>:status
checkin:<transaction-id>:wristband
checkin:<transaction-id>:transponder1
```

Each outbox row stores the exact resolved field name and value. The worker:

1. claims ready operations without allowing two workers to send the same row
   concurrently;
2. constructs the POST request from the published event endpoint;
3. sets `nohistory=0`;
4. records attempts, errors, and RaceResult confirmation time;
5. retries transient failures with backoff;
6. moves exhausted operations to conflict/attention state.

The participant becomes `checked_in` only when all three operations belonging to
the current check-in are confirmed. Partial success remains `pending_sync`.
Exhausted failure becomes `conflict`.

Repeated UI submissions must not create a second check-in or different asset
assignment for the same accepted transaction. The client supplies an
idempotency key generated before submission; the server stores it with a unique
constraint and returns the original result when it is repeated by the same
authorized workflow.

## Audit behavior

The structured `checkin.complete` audit event includes:

- transaction and check-in IDs;
- participant ID and BIB snapshot;
- volunteer ID, staff ID, and name snapshot;
- station and assignment IDs, station code, and station name snapshots;
- wristband and Transponder1 snapshots;
- authenticated session ID, device label, and source IP;
- authoritative server timestamp and optional client-observed timestamp;
- the three outbox operation IDs.

Administrative station creation, enable/disable, assignment, reassignment, and
release actions each create separate audit events. Replacements and reversals
preserve the original check-in and assignment records and append corrective
records with actor, reason, and timestamp.

Audit details must not contain PINs, session tokens, RaceResult endpoint secrets,
or other credentials.

## Error handling

- No active station assignment: reject completion with `409`.
- Disabled station: reject completion with `409` and require Admin action.
- Participant missing/wrong event: return `404`.
- Duplicate active wristband or Transponder1: return `409` without partial
  assignment.
- Identical wristband and transponder codes: return `400`.
- Duplicate idempotency key: return the original accepted result.
- Local database failure: reject without claiming success.
- RaceResult unavailable: accept locally, show pending, and retry.
- RaceResult permanent rejection: show attention/conflict without deleting or
  rewriting the audit record.

## Migration and compatibility

1. Add the station and station-assignment tables.
2. Add nullable evidence columns to `checkins`, then require all applicable
   columns for new application writes.
3. Add the transaction/idempotency uniqueness constraint.
4. Update seed data with at least one demo counter and assign the seeded
   check-in volunteer.
5. Change default and Admin mapping from lowercase `transponder1` to
   `Transponder1`.
6. Preserve published event mappings already customized by administrators; do
   not silently rewrite them during migration.
7. Document that an existing published lowercase mapping must be corrected and
   republished if RaceResult expects the case-sensitive field.

## Testing

### Unit and route tests

- Default mappings resolve to exactly `checkinstatus`, `wristbandid`, and
  `Transponder1`.
- The worker sends POST with `bib`, `fieldname`, `value`, and `nohistory=0`.
- A volunteer cannot complete check-in without an active enabled counter.
- A client-supplied station/desk value cannot override server assignment.
- Snapshot fields match participant, volunteer, station, session, and assets.
- Server time remains authoritative when client time is absent or incorrect.
- Duplicate codes roll back the complete transaction.
- Idempotent replay returns the original transaction.
- Partial RaceResult confirmation does not prematurely mark the participant
  checked in.
- All three confirmations mark the participant checked in.
- Exhausted failure marks attention/conflict and preserves evidence.
- Reassignment closes the prior station assignment without altering history.

### End-to-end acceptance

1. Admin creates `C01 – Main Gate`.
2. Admin assigns a check-in volunteer to `C01`.
3. The volunteer signs in and sees `C01 – Main Gate`.
4. The volunteer scans a participant BIB, wristband, and Transponder1.
5. HYFIT stores the complete audit record with server time and station identity.
6. RaceResult receives only the three approved fields with exact casing.
7. HYFIT displays pending and later confirmed state.
8. Internet loss leaves the check-in safely pending and later reconciles it.
9. Admin reassigns the volunteer to `C02`; subsequent check-ins show `C02`
   while the original still shows `C01`.

## Success criteria

- Every locally accepted check-in is attributable to a participant, volunteer,
  authenticated session/device, and Admin-managed counter.
- RaceResult receives only `checkinstatus`, `wristbandid`, and `Transponder1`.
- RaceResult downtime never causes loss of an accepted local check-in.
- Field casing and retry behavior are covered by automated tests.
- Historical evidence remains accurate after volunteer, participant, counter,
  or configuration changes.
